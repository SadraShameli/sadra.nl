# Engine Results Ledger

Large `bun run cli prop ...` sweeps are expensive (the 2026-09-22 sweep was about 5.6 billion simulated eval attempts and funded accounts, roughly 75 minutes on all 14 cores). Every one gets recorded here as markdown, so a question the engine already answered is looked up instead of recomputed.

Everything recorded is **engine output, per RULE #0**: produced only by the real CLI (fanned out with `xargs`) and read back from what the CLI printed. Nothing here comes from a script that imports `~/lib/prop-calculator`.

## How to use a run file

1. **Find the row** for the plan, objective and inputs you need. Every table states its horizon, seeds, trials and policy set.
2. **Check it is not stale** before citing it. A run is only valid for the engine and firm data it was computed on, and both live in git:
   ```
   git log --oneline <engine_commit>..HEAD -- src/lib/prop-calculator src/cli/commands/prop
   git status --short -- src/lib/prop-calculator src/cli/commands/prop
   ```
   Any commit that touches `src/lib/prop-calculator/firms/<firm>/` makes that firm's rows stale; any commit that changes simulation behavior, CLI defaults (`src/cli/commands/prop/shared.ts`) or a printed metric makes the whole run stale. Say which rows are stale when citing them, and re-run only those.

   **Any `optimize dp` funded-DP number or ADOPT/KEEP verdict measured before 2026-09-25 is stale regardless of the checks above**: two defects in `FundedStateValue.ts` (N-65, an optimistic carried best-day state; N-66, an under-converged stopping rule) were fixed in waves 16-17 of the prop-engine audit (`.claude/plans/prop-engine-audit-2026-09-23/PLAN.md`). Mark such a row stale for that reason even if its firm files and printed metric are unchanged. The eval-only DP (`EvalStateValue.ts`) is a different module and N-65/N-66 do not apply to it, but its own pre-2026-09-25 numbers are stale too, for unrelated reasons: N-9 (no risk cap at the remaining DLL headroom, fixed wave 8) changed `EvalStateValue.ts` itself, and WP22a (wave 15) moved it onto an intraday-reach tier basis. Mark a pre-audit eval-DP row stale for those reasons instead.
3. **Hold the objective fixed.** Read the metric definitions below before comparing two numbers; mixing `monthly net` with `lifetime net` or with `per-cycle net` is the mistake this ledger exists to prevent (SKILL.md mistake 15).
4. **Re-running**: each run file lists the exact CLI command template and plan list for every stage. Fan the jobs out with `xargs -L1 -P<cores>` over one-job-per-line lists, run the eval ladder stage first (the funded stages read each plan's fastest ladder from it), and use a fresh output directory per run.
5. **Recording a new run**: add a new `engine-results/<date>-<name>.md` with the same sections (inputs, stages with command templates, result tables, adjustments, verification, artifacts), then add a row to the Runs table above. Never edit an old run's numbers; if a later run supersedes one, say so in its Status cell.

## Metric definitions (shared by every run)

| Metric | Engine source | Meaning | Valid for ranking plans against each other? |
|---|---|---|---|
| **monthly net** | `expectedMonthlyNet` = `(expectedNet + expectedHorizonCredit) x 21 / (expectedDaysPerTrial + rebuyLagDays x expectedAttempts)` (`simulator/engine.ts`); printed by `optimize funded` (`--sort monthly`, the default) and `optimize dp` | steady-state net cash per month for ONE account slot, refilled after every failed eval, funded bust or horizon end; an account still alive at the horizon is credited its withdrawable balance (`expectedHorizonCredit`, one payout request net of split, scheduling/qualifying-day gates ignored); `--rebuy-lag-days` (default 0) charges empty slot time per new eval attempt | **Yes.** Caveats: assumes instant, unlimited repurchase past `--rebuy-lag-days` (no purchase caps); the horizon credit models the withdrawable balance, not the days a real payout request takes to arrive (no payout lag modeled) |
| **monthly ex-credit** | `expectedMonthlyRealizedNet` = `expectedNet x 21 / (expectedDaysPerTrial + rebuyLagDays x expectedAttempts)` (`simulator/engine.ts`, same slot days as monthly net); printed next to monthly net and the horizon credit by `optimize funded` | monthly net includes the horizon credit, monthly ex-credit leaves it out, so a row whose lead comes from an end-of-horizon lump sum shows at a glance. A `--request-size` below the largest single-day profit turns the policy into "hoard, then cash out at the horizon": each request leaves the excess in the account, so the cushion grows and more accounts survive, but the hoarded balance only pays at the horizon, where the credit is at most one capped request (T32), and $0 on a daily-payout plan whose last payout emptied the cycle-profit pool | Not the default ranking (`--sort monthly` still ranks on monthly net, U17). Compare the two columns before trusting a row that beats its neighbours only on monthly net |
| lifetime net (removed from the engine) | `lifetimeExpectedNet` = `(expectedNet - pBust x feesUntilPass) / (1 - pBust)` (formerly `core/LifetimeExtraction.ts`, deleted) | "repeat until one funded account survives the horizon" | **Removed, 2026-09-23.** No time cost, so it diverged as pBust approached 1 (Tradeify Lightning flat $300 scored $1.53M); it renewed only after a funded bust, never after a failed eval; the `- pBust x fee` term charged each renewal's fee twice, because each cycle's `expectedNet` already contained it. SKILL.md Hard Rule 8 named lifetime net as the funded objective; it was rewritten to name monthly net (replacement priced in) instead of being reconciled with this metric |
| per-cycle net | `expectedNet` | net of one attempt: eval fees plus funded payouts inside the horizon | only for one bounded run; never across plans with different attempt lengths |
| **cost per funded account** (D1) | `costPerFundedAccount` = `replacementEconomics(...).costPerFundedAccount + fundedResetFeesPerFundedAccount` (`core/Replacement.ts`, `simulator/engine.ts`); printed by `sim`, `compare` (`--sort cost`) and `ladder` | full expected spend to acquire one funded account: the initial eval fee (bundle discount applied) plus `(1/p − 1)` retries, where `p` is the per-attempt eval pass rate (`reachedFundedCount / attemptsSum`, not the same figure as the "eval pass" row below), each retry priced at whichever of reset or re-buy is cheaper for that plan (T9), the subscription months actually billed over the renewal chain, activation paid once on the pass, and (on a funded-reset plan, T31) reset fees added on top, divided by the accounts that passed the eval | Yes, for "how much does one funded account cost", across plans with different reset/re-buy/subscription structures. Never compare it to `expectedTotalCost` ("spend"), which is per trial, not per funded account |
| **eval pass** | `evalPassProbability` = `(counts['pass-clean'] + counts['bust-funded']) / trials` (`simulator/engine.ts`) | share of trials (one trial can hold up to `--max-attempts` eval attempts) that reached the funded phase at all, whether or not the funded account later busted (D2) | Yes, for "how likely is the eval itself to be passed". `compare --sort pass` sorts by this, not funded survive |
| **funded survive** | `fundedSurvivalProbability` = `counts['pass-clean'] / trials` (`simulator/engine.ts`) | share of all attempts that passed the eval AND finished the funded horizon unbusted (same event as "survivors" below, expressed as a rate) (D2) | Yes, but never as a stand-in for eval pass. Both are always shown side by side (D2), not merged into one "pass rate" |
| bust when funded | `counts['bust-funded'] / trials` | UNCONDITIONAL share of all attempts, so it can never exceed the eval pass rate | read as "share of all attempts", not "share of funded accounts" |
| survivors | `passProbability x trials` | attempts that passed the eval AND finished the funded horizon unbusted | small counts mean a noisy row |
| pass / days / $ per funded | `prop ladder` | eval pass probability, expected days to funded, cost per funded account (D1, the same `replacementEconomics` formula `sim`/`compare` use) | eval phase only |
