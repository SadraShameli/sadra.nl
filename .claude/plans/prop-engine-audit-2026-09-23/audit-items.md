### R1-2: cost / funded acct and cost / drawdown $ leave out reset fees and understate true cost when --max-attempts > 1
- Location (as reported): src/lib/prop-calculator/simulator/engine.ts:213
- Reviewer severities: B=medium, C=medium
- Finder description: replacementEconomics gets evalPrice = activation + eval + monthly subs, without resetFeesTotal, and multiplies it by 1/passRate. The correct value is expectedTotalCost / passProbability.
- Finder failure scenario: topstep standard-standard, risk 500, max-attempts 5, seed 7: the tool reports $1,725 per funded account. The correct figure is 244 / 0.115 = about $2,122, so the tool understates it by about 23%.
- Reviewer B (real=True): Confirmed with small corrections. In simulate() (src/lib/prop-calculator/simulator/engine.ts:211-219), the evalPrice passed to replacementEconomics is perAccountActivationFee + perAccountEvalFee + monthlySubsTotal. It leaves out the expected reset fees per trial (costBreakdown.resetFeesTotal / avgResetFees). With --max-attempts > 1, each trial is a purchase plus up to N-1 paid resets. passProbability is the success rate per bundle, so Replacement.ts's evalPrice * (1/passRate) prices every bundle as if it had no resets. Result: 'cost / funded acct' and 'cost / drawdown $' are understated for any plan with a nonzero reset fee. Example: TopStep standard-standard, risk 500, max-attempts 5, seed 7, 4000 trials shows $1,711 (= $198 / 0.116). The per-bundle cost including resets gives about $244 / 0.116, roughly $2,100, so the shown figure is about 19-23% low. The report's $1,725 and 11.5% differ slightly from my run, probably because of a different trial count. With the default max-attempts=1 there are no resets and the bug does not appear. The metric appears only in `prop sim` output and does not feed any ranking or optimizer. Two related issues the report did not raise: (a) the denominator is the pass-clean rate (reached funded and did not bust within the horizon), not the rate of reaching a funded account; (b) the activation fee is multiplied by 1/passRate although it is only charged on passing. Both affect how the figure should be defined, but the reset-fee omission is wrong under either definition.

### R1-3: expectedFirstPayoutDay leaves out trials that were paid and later busted (survivorship bias)
- Location (as reported): src/lib/prop-calculator/simulator/engine.ts:142
- Reviewer severities: B=medium, C=medium
- Finder description: The first-payout average only counts trials where the outcome is pass-clean. bust-funded trials that did get a first payout are dropped. This does not match the other payout aggregates in the same function, or livePhase.ts.
- Finder failure scenario: On plans where funded accounts bust often, the First payout day shown in ResultsPanel is averaged only over trials that never busted, so the figure is biased.
- Reviewer B (real=True): engine.ts:142 only adds a trial to the first-payout average when isPassingOutcome(r.outcome) is true, and that is true only for 'pass-clean'. trial.ts sets firstPayoutDay whenever the funded phase paid out, before it decides whether the account later busted. As a result, a trial that received a first payout and then busted in the funded phase ('bust-funded') is left out of expectedFirstPayoutDay. The statistic is therefore conditioned on a future event (surviving the whole funded horizon), and the average is taken only over survivors. On plans where funded accounts nearly always bust within the horizon, the result collapses to 0, which the web UI (ResultsPanel.tsx:255) shows as '—'. Concrete case, pinned in engineCharacterization.test.ts: MFFU Rapid EOD 50k, seed 42, 200 trials, 252-day funded horizon, $400 risk, 2R, 50% WR. It gives expectedGrossPayout $10,270.8 and fundedBustProbability 0.815, but expectedFirstPayoutDay 0. TPT Test-to-PRO 50k behaves the same way. The correct estimator averages over every trial with firstPayoutDay !== null (pass-clean or bust-funded). The bug affects only this display KPI in the web UI. It does not feed expectedNet, monthly net, rankings or any CLI output, so I rate it medium rather than high.
- Reviewer B verified via: Traced engine.ts:126-145 and 266-267, trial.ts:11-13 and 61-111, fundedPhase.ts:47-57 and 168-230 (PayoutTotals records firstPayoutDay whenever a payout happens, and the bust status is decided afterwards). Checked the history in git show 26d7188^:simulator.ts: the filter was the same then, and isPassingOutcome was pass-clean or pass-violation. Found the only consumer, ResultsPanel.tsx:255, and its description in kpiDescriptions.ts:17. Ran bunx vitest run tests/unit/lib/prop-calculator/engineCharacterization.test.ts (66 passed), which pins expectedFirstPayoutDay = 0 for MFFU Rapid EOD and TPT while expectedGrossPayout is $10,270.8 / $7,932.8 and fundedBustProbability is 0.815 / 0.83.
- Reviewer C (real=True): Confirmed at src/lib/prop-calculator/simulator/engine.ts:142. expectedFirstPayoutDay averages firstPayoutDay only over trials whose outcome is 'pass-clean' (isPassingOutcome). Trials that received a first payout and later busted the funded account ('bust-funded') are left out, even though trial.ts:84-87 records their firstPayoutDay. The metric is therefore conditioned on the account surviving the whole funded horizon, which is a later event. That is survivorship bias, and it does not match the KPI description ('Calendar day of the first eligible payout') or the other payout aggregates, which count bust-funded trials. The effect is worse than a bias when funded busts are frequent. The characterization test pins MFFU Rapid EOD 50k (risk $400, RR 2, 50% winrate, 2 trades/day, 252-day horizon, seed 42) at fundedBustProbability 0.815, expectedGrossPayout $10,270.80 and expectedFirstPayoutDay 0, so the web UI 'First payout' KPI shows '—' although most trials were paid. TPT 50k shows the same result. The fix is to filter on outcome in {pass-clean, bust-funded}, or simply on firstPayoutDay !== null. Impact is limited to that one web UI KPI: the CLI does not print it, and it does not feed expectedNet, monthly net or any ranking. Severity: medium.
- Reviewer C verified via: I traced engine.ts:126-145 and 266-267, trial.ts:11-13 and 84-105, fundedPhase.ts:46-57 and 222-229, ResultsPanel.tsx:247-258 and kpiDescriptions.ts:16. ### R1-7: dayCloseValue assumes every prior funded payout drained the account exactly to the payout floor, inflating cross-cycle profit for ladder-style payout plans
- Location (as reported): src/lib/prop-calculator/core/FundedStateValue.ts:634
- Reviewer severities: B=medium, C=medium
- Finder description: When regimeAtStart > 0, tracker.lastPayoutBalance is seeded with plan.payoutBalanceFloor(...) instead of the actual balance right after the payout. With fixed-step payout ladders, the real post-payout balance sits above the floor, so cycleProfit comes out too high.
- Finder failure scenario: MFFU Builder has a ladder of [2000 x5], minPayoutProfitPerCycle $500 and 50% funded consistency. In the second and later cycles, the inflated cycleProfit clears the minimum-profit gate too early and makes the consistency check too easy to pass. This overstates payout speed and expected value.
- Reviewer B (real=True): In the funded value-iteration DP (src/lib/prop-calculator/core/FundedStateValue.ts:634-637, dayCloseValue), every state with regimeAtStart > 0 rebuilds the payout tracker with lastPayoutBalance = plan.payoutBalanceFloor(state, retainedCushion). It does not use the account's real balance right after the last payout, because the DP state does not store that balance. The real FundedCycleTracker.tryPayout measures cycleProfit from the actual post-debit balance. So whenever a payout leaves the balance above the floor, the DP overstates cycle profit in every later cycle. Payouts that leave the balance above the floor come from a fixed ladder step smaller than withdrawable, or from a request or profit-share cap. The inflated figure loosens the minPayoutProfitPerCycle gate and the per-cycle funded consistency check. Example with MFFU Builder 50K (floor $52,100): a $2,000 ladder payout from $55,000 leaves $53,000. After two -$100 days at $52,800, the DP credits a $700 payout ($560 to the trader) for a cycle whose real profit is -$200, which builder.md's '$500 net profit since the last approved payout' rule would deny. This affects only the DP path, which is `cli prop optimize dp`: its printed 'DP-predicted average reward' is optimistic and its state-dependent funded policy is optimized against looser rules than the real ones. The Monte Carlo validation run in the same command uses the correct tracker, so its empirical figures are right for the policy it is given. The CLI warns about other DP gaps but not this one.
