## Goal

Three deliverables, in dependency order:

- **(A) Page split.** Split the 427-line `/prop-calculator` page (`CalculatorShell.tsx`, 15 stacked sections, about 9 simulation batches per keystroke) into a hub with child tool pages. Every existing panel moves with no behaviour change, and old share links (query and section fragment) keep working.
- **(B) Accounts manager.** A DB-backed prop accounts manager behind sign-in:
  - accounts, balance snapshots, payouts, fees, lifecycle events, copy groups and a personal rulebook;
  - an overview built from every metric the code and the rules support, led by spend, payouts received and realized net.
- **(C) Per-account sizing suggester.**
  - The headline is the user's documented rule (prop-firm-trading skill, Hard Rules 1 to 8).
  - The engine optimum sits alongside it, with a typed reason for every difference.
  - Every number carries its source rule, its assumptions and its start basis.
  - Every engine run uses the user's retained cushion, the effective payout request (the larger of the rulebook size and the plan's minimum) under the "wait for the full request" policy, and the verified live-trigger payout cap, never the plan's own defaults. Where an engine source cannot honor that policy, the row says so with a typed reason.

## API (`propAccounts` router in `src/server/api/root.ts`, nested like `routers/lifting/index.ts`)

All procedures use `protectedProcedure`, with Zod `.input()` and `.output()`.
- Every select, update and delete on `sadranl_prop_*` has `"user_id" = <session userId>` in its WHERE clause, including inside `tx` (ESLint does not cover `tx`, `eslint.config.js:74-81`).
- Child writes first call `loadOwnedAccountOrThrow(accountId, userId)` (NOT_FOUND on miss); every `snapshot_id`, `copy_group_id` and `replaces_account_id` is ownership-checked the same way on every path that sets it (create, update, importMany rows, copyGroup.assign, decision.create), and a snapshot must belong to the decision's account (`id`, `user_id` and `account_id` all match). `copyGroup.assign`'s mixed-stage check runs on create, update and importMany too. Removes clear the referencing columns first in the same transaction (PD-20). A Postgres unique violation on the active label (23505) maps to CONFLICT with a readable message, never a 500.
- Mutations pass the rate limit and per-user row caps (PD-36).

## Suggester design (part C)

The code lives in `src/lib/prop-calculator/advisor/` (browser-safe barrel `~/lib/prop-calculator/advisor`). DP code lives in `advisor/dp/` (Node-only, never re-exported, PD-16). An import-graph test proves the barrel never reaches `FundedStateValue.ts`, `AverageRewardSolver.ts` or any `node:` module.

**Documented rules.** `DocumentedRule` is the abstract base. Subclasses: `EvalLadderRule` (default, general derivation; MFF search fractions opt-in), `EvalMaxRiskRule` (opt-in), `FundedFixedRiskRule`, `LiveCushionPercentRule`, `PayoutRequestRule` (PT-46).
- Input `RuleContext`: cushion, day-start DLL room (or none), personal DLL (or none), consistency daily cap (or none), profit target and remaining profit to target (eval), rr, lock state, the plan's contract limit and instrument for the minimum-stop report, the live cushion percent resolved by the plan's applicable `LivePlan` (PD-41, built with the rulebook's `LiveCushionPercent`, then `cushionPercentFor`), and for payouts the reconstructed tracker, `evaluatePayout` result and effective request. Caps arrive as inputs computed by `resolveRiskAt` (PT-13) and the plan's own methods; rules never re-derive `plan.affordableRisk`.
- Output `DocumentedSizing`: rungs, TP per rung, daily profit cap, `DayStopRule`, max trades, running-loss column, `minStopPointsAtCap`, notes and `RuleSource[]` (section anchors). The funded rule also states its trades per day and stop rule, which `EnginePolicy` carries.
- Live risk goes through `resolveLiveTradeRisk` (`core/LiveSizing.ts:20`); E8/FTMO (no live builder) select the rulebook percent by the reconstructed lock flag and call the same function.
- They are pure and instant. `DocumentedPolicySpec` plus `toSimInputs` (PT-48, PD-39) make the same rules runnable by `simulate`.

**Reconstruction.** `AccountReconstruction.rebuild(snapshotInput, plan)` returns a `ReconstructedAccount`: plan with opt-ins, phase, full `AccountState` (including peak day-close profit, peak intraday profit, intraday high, best day, qualifying days, consecutive idle days, elapsed days), `FundedCycleTracker` (including `fundedResetsUsed` in its `cycleSnapshot`) or live state, floor, lock, cushion, resolved DLL and contract limit, `Assumption[]` and warnings. The steps:
1. Validate plausibility (F-140): a pre-lock cushion above the plan's drawdown on a trailing plan, a nominal balance far from the account size, or a $0-based balance near the account size fail loud with the likely convention error.
2. Start from `plan.initialState()` or `plan.beginFundedPhase` (`Plan.ts:723-728`, `636-650`; re-read after G2).
3. Replay the peak through the plan's own `DrawdownStrategy`. For lock-effect plans use the floor at last payout when given; otherwise take the conservative order and disclose it.
4. Apply `payoutFloorEffect` for payouts already taken.
5. Seed the tracker's public fields (payouts issued, cumulative payout as trader-received net, `fundedResetsUsed` from events) and calendar-gate progress from real dates.
6. Cross-check a given dashboard floor: keep the higher floor and warn on mismatch.
7. Build the live stage from the plan's applicable live builder (PD-41; `LiveModelApproximation` where only a firm-level builder exists; TopStep reserve state from the live start balance plus disclosed defaults); E8/FTMO "not modeled", the documented live rule still works from the dashboard floor.

**Payout readiness.** A core enum `PayoutGate` (`core/PayoutGate.ts`, exported from `core/index.ts`) has one member per null-returning branch of `tryPayout` (including early withdrawal and `resolveWithdrawal`'s ladder, min-request and deny-if-unaffordable checks), plus `AccountConcluded` (`Plan.isAccountConcluded`, lifetime payout count, `Plan.ts:811-819`) and `LadderExhausted` (closeout-credit ladder). The new non-mutating `FundedCycleTracker.evaluatePayout` (extracted from `tryPayout`) returns a `PayoutGate` or eligible plus amount. The advisor-level `PayoutBlockReason` (`advisor/PayoutBlockReason.ts`) wraps it as a union: `{kind: Gate, gate}`, `{kind: PayoutPending}` (an open Requested payout), `{kind: WouldTriggerLive, trigger}` (declared in PT-12, returned only once PT-36 supplies verified triggers). Core never imports advisor. `PayoutReadiness` builds on both.

**Advisor.** `SizingAdvisor` is the abstract base with `EvalSizingAdvisor`, `FundedSizingAdvisor` and `LiveSizingAdvisor`, built by `createSizingAdvisor(stage, plan)` (instant-funded plans reject Eval). API:
- `documented()`: sync; stale snapshots per PD-28 return `StaleAdvice` with no amounts.
- `caps()`: `RiskCaps` from `resolveRiskAt` plus personal caps.
- `optimumRequests()`: serializable `EngineOptimumRequest[]`, each carrying the full `EnginePolicy` (PD-26).
- `assemble(results)`: an `Advice` holding headline (with custom-rule label), optima, `DifferenceReason[]`, assumptions (including "live triggers not checked" until PT-36), `Provenance`, `DailyPlanCard` and `PayoutAdvice`.

**Daily plan card.** Rungs and TP with running loss, daily cap, stop conditions and one trade per window (Hard Rule 6). When a ceiling applies (the funded consistency maximum before the payout is pushed out, or a verified single-day live trigger from PT-36), every rung is capped at `(ceiling - running PnL) / rr` after the documented and DLL caps, and the card shows "stop for today" once that cap falls below the placeable minimum (one micro contract at the entered stop, else $1). It never suggests an early exit (Hard Rule 1).

**DP strategy (PD-16).**
1. One solve per distinct full config: every parameter the solver honors (plan serial, opt-ins, plan-rule fingerprint, winrate, rr, tpd, commission, grid, rebuy lag days, funded-days hazard, eval days, fees and discounts, day-stop rule, cushion-step multiple, retained cushion, and after PT-47 the effective payout request and policy) is hashed into `config_key`. `prop advise --dp` passes `fundedGrid.minRetainedCushion` from the rulebook (today `optimize dp` passes no `fundedGrid` at all).
2. Eligibility via `isFundedDpEligible` and `isEvalDpEligible`, computed in the CLI and stored with the reason.
3. Model gaps from `fundedDpModelGaps`, plus a state-fit report for grid saturation, plus `PayoutSizeNotModeled` when PT-47 is not in place. `DpGridMisaligned` (eval drawdown not a multiple of `cushionStepDollars`) is informational only: the skill calls an even divisor "necessary-looking but not sufficient", and AlphaFutures Advanced ($1,750 drawdown, $200 step) was measured ADOPT.
4. Eval: reached-state query (PT-18); elapsed sessions mapped explicitly to the DP day index; states past the solve's eval-days horizon give `DpStateUnreached`; the funded `computeRisk` throw for unreachable levels is caught into a typed reason.
5. Objective shown in provenance. Eval DP rows appear only for plans with a current eval-DP validation under the cash objective (terminal value at pass tied to the funded continuation value) recorded in the ledger; otherwise they are suppressed with `DpNotValidated`, and a pass-probability objective is suppressed with `DpObjectiveMismatch` (every eval-DP verdict in the skill is historical, pass-probability).
6. `validated` is true only from a post-G2 gate run recorded in the ledger with its engine commit, a retained cushion matched between the DP and the flat baseline (PD-26), and DP >= the best flat policy by the gate; otherwise "not validated" with the gate result named. The 2026-09-23 validation-2 file does not qualify (stale tree on 65e310c; TopStep ran at a $0 retained cushion against a $2,000 flat baseline and scored 0.99x). PT-30 re-runs the gate and appends the ledger row.
7. Staleness: newer snapshot, different `solver_version`, or different plan-rule fingerprint. A pinned toy-solve characterization test forces a `DP_ADVICE_SOLVER_VERSION` bump.
8. A per-run plan cap and time budget with resumable per-plan output; runtime printed.
9. Verified conduct clauses against aggressive day-1 sizing (for example TopStep FTP Slowdown / RTP, FTMO inconsistent position sizing, if PT-04 confirms them) attach `AggressiveOptimumChurn` with the firm's quote to DP rows and sweep rows alike.

**Reasons (`DifferenceReason`, text from typed fields, all declared in PT-19):** ObjectiveSpeedVsMonthlyNet, FreshStartApproximation, AggressiveOptimumChurn (only from a verified conduct pattern, with the quote), WithinNoise (only where SEs exist, PD-34), CushionCap, DailyLossCap, ConsistencyCap, RemainingTargetCap, CeilingCap, PersonalCap, RetainedCushionBasis, FirmMinimumAboveRequest, PayoutPolicyDiffers, DpIneligible, DpModelGap, DpGridSaturation, DpGridMisaligned (informational), DpStateUnreached, DpObjectiveMismatch, DpNotValidated, DpPayoutPolicyMismatch, ConsistencyNotEvaluated, AssumedInputs, StaleAdvice, LiveNotModeled, LiveModelApproximation, LiveTriggersNotChecked, WouldTriggerLive, PlanRulesChanged.

## Page split design (part A)

Route tree:

```
src/app/(app)/prop-calculator/
  page.tsx                       hub (public, dynamic like every route; renders its own <main>)
  (tools)/layout.tsx             server layout: client CalculatorProvider, subnav, <main> around children
  (tools)/simulator|analysis|sizing|compare|cash-flow|ladder-lab|strategy-lab|planner/page.tsx
  (tools)/position-size|funded-optimizer|live|rules|payout-planner/page.tsx
  accounts/layout.tsx            session guard, noindex, subnav
  accounts/... (overview, new, [id], [id]/edit, review, ledger, import, rulebook, copy-groups, next-slot, edge)
  _components/ (unchanged location: 19 tests import it, knip.json:7 entry, worker URL in useLadderSearch.ts:268)
  _workers/
```

- **State:** `CalculatorProvider` splits four contexts: inputs state (reducer state and firm memory), base result plus pending flags, lab slots (pinned, chartType, ladder slot), and memoized actions (created once over `dispatch`). The computation cache lives in a ref, never in React state, so writes never re-render consumers. The ladder slot is written only on completion, cancel or unmount. The reducer is initialized lazily from `useSearchParams()` (PD-8 a); the legacy hash is handled in a mount effect before the first URL write; one writer on `[state, pathname, searchParams]`.
- **Computation cache:** namespaced by a `ComputationId` enum (BaseSimulation, RuleStress, OptimalRisk, Sensitivity, PlanComparison, FirmComparison, CashFlow, Planner, StrategyLab), typed through a `ComputationResultMap` so `get`/`set<Id>(id, key)` return that id's result type. A pure `initialFor(id, key, cache)` returns `{result, pending, shouldCompute}` and drives `useDebouncedComputation`'s `useState` initializers and an early return in its mount effect, so a cache hit neither flashes nor recomputes.
- **Navigation:** `RouteSubnav` items are keyed by base route, carry the debounced query with `prefetch={false}` (PD-8 d), and the active item is resolved across the whole list by `activeSubnavHref(pathname, items)` (most specific match wins, so a Prefix parent never shares `aria-current="page"` with an exact child); the `<nav>` gets an `aria-label`. `SectionNav` is retired (both render into `#navbar-subnav-slot`, `Navbar.tsx:67`).
- **Hub round trip:** the hub is outside the provider. The last encoded query is kept in sessionStorage (try/catch) and appended to hub card hrefs, so inputs survive; pinned scenarios and lab results reset on leaving the tools area, and the hub says so.
- **Loading:** each page imports only its panels. Heavy panels load through `next/dynamic` with `Skeleton` fallbacks. Result-consuming sections render a `Skeleton` until the base result is non-null (PD-10).
- **SEO, headings and landmarks:** each page exports `metadata` (title, description, canonical without query) via `buildToolMetadata(ToolId)`. The layout owns `<main>`; `ToolPageHeading` renders the `<h1>` then the toolbar; each section is a `<section aria-labelledby>` with an `<h2>` (PD-7). Tool pages go in `indexableRoutes`, accounts in `disallowedCrawlPaths` (`routes.ts:68-88`). The stale "6 firms" description (`page.tsx:9`) is fixed from `ALL_FIRMS` (10).
